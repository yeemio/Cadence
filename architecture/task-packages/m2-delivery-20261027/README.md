### B. 安全波 b：SP-3＋CM-1；R1 加入裁-12

- **SP-3** 按原合同固化附件与图纸两域签名密钥配置，验证合法配置透传、非法配置拒启动、相同密钥下重启后的引用可用；不改变 TTL、租户、访问与留痕语义。
- **CM-1** 按 SP-6 已登记建议补安全响应头：CSP、`nosniff`、Referrer-Policy、frame 限制。结合实际静态资源与代理拓扑在一个明确权威层配置，并验证浏览器真正收到这些头；不能只在 JSON API 上生效而遗漏 HTML 页面。
- CSP 验证覆盖登录、桌面、移动、静态资源及实际使用的连接路径；不得用放开全部来源或移除既有安全约束来消除报错。具体策略需与真实加载方式相符，不机械复制示例。
- main.ts、app-registry、nginx 与多语言／错误呈现的共享写入面由原总控串行安排，不重启第二个 writer 抢写。

**裁-12：图纸通知与关联修订的可见权限一致。** 原决策队列记录 `/drawing/notices` 虽有 `drawing:read` 门禁，却未按 clearance 过滤，受限修订的 `changeNote` 可能被较低许可用户读到。本轮先在接收时的准确候选核实该具名路径；已被在途修复覆盖时接收有效证据，不能把历史记录直接当作当前仍可复现的缺陷。

- 本轮处理目标采用原选项 A 的保证：沿用关联图纸修订的现有 clearance／租户可见规则，服务端只向有权用户返回相应通知。既有 `drawing:read` 门禁继续保留；不新增保密等级或权限体系。
- 过滤必须在服务端返回数据之前完成；前端隐藏、仅改提示词或仅脱敏一个字段，不能代替“通知随关联修订权限可见”的要求。只修复该通知链实际涉及的查询、序列化和消费接缝；如已有分页／计数，须与过滤后的可见结果一致。
- 用同一受限修订证明：具有 `drawing:read` 但 clearance 不足的用户看不到受限通知及其变更内容；有权用户仍能看到应有通知；普通可见通知保持可用，租户边界不退化。复用岗位夹具，保留服务端响应与实际通知入口读回，不能只交页面截图。

3. 稳定增量进入准确候选，补受影响测试与运行证明；按本仓合同执行一次适用的全仓 `pnpm verify`。同候选有效结果可复用，后续只因真实改变或失败重跑相关覆盖。
4. 完成具名角色剧本与干净安装的缺失证据；修复本轮具名阻塞，保留首次失败。不要顺带清空历史待办或追加整仓审计。
5. 冻结候选并交只读审查；审查期间不修改所交候选。另有工作必须隔离。最终回传交付、审查、未决事项及唯一下一动作，由产品接收方给出 ACCEPT／REWORK／BLOCKED。

同一根因连续两次针对性修复仍未关闭具名缺口，或出现新的权限／产品语义边界时，原 writer 保留候选和证据，由原工程总控判断缩小或调整合同；不要自动换模型、重建任务或扩容。同一候选的返工保留原 writer。

正常停止点为稳定交付与审查原件已备齐、等待产品接收；真实外部等待或精确决定缺口时，返回具体阻塞及恢复输入。账户／API 限制按平台退避，不规避限额。

**本轮不得扩入**：首个客户选择、真实数据导入、生产发布、多人报工、完工／撤销规则、S14 精算、计费与运营平台、全量英语翻译、D-22 导出实施。若 Owner 已在本包之后对某项另下指令，以该指令建立明确差量，不能冒称本包原范围。
